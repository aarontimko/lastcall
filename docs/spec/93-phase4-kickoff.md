# Phase 4 Kickoff Prompt (operational artifact, not design)

**Rulings: pending.** The adversarial design review ran on 2026-09-02 (19 findings, all folded into this revision — record in `z_ignore/review-phase4/`); next the sponsor rules on the items under "Open for ruling" at the end; this header is rewritten with the verbatim verdicts (recorded in `00-spec.md` §10) before any worker exists.

Phase 4 of the lastcall phased program. Phase 3 closed on 2026-09-02 (PR #3, merged `1d8f998`): the read-only TUI exists — header, nav, diff view, live updates, mouse plus keyboard, a `[keys]` config table — on top of the Phase 2 engine, which already contains every accept operation as a library call (`ops.rs`: `accept_file`, `accept_hunk`, `accept_deletion`, `accept_group`, `accept_all`, with compare-and-swap, the ledger lock, cross-engine merge and compaction; 52 integration scenarios exercise them headlessly). Nothing on screen can accept yet. This phase wires the accept loop into that exact UI — accept hunk, accept file (and deletion, and the upstream group), accept all — with persistence and restart resume proven end-to-end, and it records the program's **performance baseline** (§10 amendment of 2026-09-02) including the per-root row cap. It closes Gate 4 (§8, Phase 4). **No restore, no flag, no editor** — those are Phases 7 and 8. This is the product moment: "the pile visibly shrinks" (§6.7) is a requirement, not a nicety.

**The spine of this phase is invariant 2 (§2) applied to a write path: the tool over-shows and never hides, so every accept blesses exactly what the user saw and nothing else.** The UI still never reads a file, never diffs, never spawns git (single spawn site `git.rs`, gate grep). What changes is that the UI now hands the engine a *rendered snapshot* — `ops::Rendered::of(&row)` built from the row the `App` drew, or the whole held `Pile` for accept-all — and the engine's compare-and-swap (§6.3) refuses the accept if the live file moved since that render. A refusal is not an error: the status line says why (`ops::Refused`'s `Display` text is the user-facing sentence) and the fresh pile re-renders with the newer content still pending. Second rule of the spine: **one critical section per accept.** The accept and the rescan of that root run inside one `blocking` closure under the engine mutex, so the pile that comes back is the pile after the accept, and no watcher scan can interleave between them. Because the watcher may still publish an *older* pile a moment later (§11 deferral "two channels", whose trigger — Phase 4's accept path — fires now), every pile carries an engine-wide scan sequence number and the reducer drops anything older than what it holds for that root (and forgets the number when a root is removed, so a re-added root is never silenced). If you find yourself building a `Rendered` from engine state instead of from the `App`'s held row, stop: that defeats the CAS, because the engine's row may already be newer than what the user is looking at.

**The reference implementations:** `crates/lastcall-engine/tests/common/mod.rs` (`Fresh`: `accept_file`, `accept_hunk`, `accept_all_snapshot`, `restart`, `ledger` — the exact call shapes and the restart idiom every new test reuses), `crates/lastcall-engine/tests/test_integration_scenarios_a.rs` (A2–A7: what an accept must leave in the ledger and the pile), `crates/lastcall/src/tui/run.rs` (`spawn_refresh` / `joined`: the shape of an off-task engine call that reports back on the local channel), `crates/lastcall-engine/tests/test_perf_scan.rs` (the `#[ignore]` + `PERF` lines shape the bench imitates), and `crates/lastcall/tests/test_e2e_tui_pty.rs` (the scenes the scripted agent loop extends).

## Deliverables

1. **Engine additions (additive; `cargo check -p lastcall-engine --no-default-features` stays green).**
   - (a) **Scan sequence.** **Engine-global**, not per root: `Engine.scan_seq: u64`, incremented by every scan of any root (`scan`, `scan_all`, the HEAD-change rescan) and never reset while the process lives — a per-root counter would restart at 0 when `rescan` drops and re-opens a root, and the reducer would then drop every later pile as "older" (review F1). Every pile publisher carries the number of the scan that produced it: `EngineEvent::Pile { root, seq, pile }`, `HeadChange { …, seq }` (the second publisher, `watcher.rs`'s head-change arm), and `scan_all` returns `Vec<(PathBuf, u64, Result<Pile, EngineError>)>`. `watch.rs`'s `print_event` prints it (`pile alpha #7 …`). Nothing else in the engine reads it.
   - (b) **`Engine::accept(&mut self, root: &Path, req: AcceptRequest) -> Result<Accepted, EngineError>`** where `enum AcceptRequest { Hunk { rendered: Rendered, hunks: Vec<Hunk>, index: usize }, File(Rendered), Group(Vec<Rendered>), All(Pile) }` and `struct Accepted { outcome: Outcome, seq: u64, pile: Pile }`: runs the op through `self.ops(root)?`, then `self.scan(root)` — one call, one critical section, the post-accept pile returned with its seq (the borrow shape `self.ops(root)?.accept_file(..)?; self.scan(root)` compiles under NLL — verified). `accept` is `accept_with(root, req, &NoFault)`; `pub fn accept_with(&mut self, root, req, fault: &dyn FaultInjector)` exists so E1 (crash mid-accept) is testable through the path the TUI uses. `File` with `rendered.oid == None` routes to `accept_deletion`. `OpsError` maps through the **existing** `EngineError::Ops` variant — add no second one. Unit-tested in the engine (in-module fixtures in the `store::tests::fixture_env` style, not the integration tier's `Fresh`) for each variant, including a refusal (the pile still returns and still shows the row), plus E1 through `accept_with`: a fault at `AfterLedgerTmpWrite` → `Err(EngineError::Ops(..))`, the on-disk ledger unchanged, the next scan's pile identical to the pre-accept pile.
   - (c) **Per-root row cap.** `EngineOptions.row_cap: usize` (default = ruling 1; `Config` gains no key in v1). In `scan`, candidates are **partitioned before hashing**: the priority set P = override keys ∪ flagged paths (bounded by the compaction threshold plus flags) is always materialised; every other candidate — `diff-files` entries, `others`, case-rule and unparsable paths alike, so a 50,000-file branch switch is capped exactly like a 50,000-file drop — is taken in path order until `row_cap` rows have been materialised (hashing and hunks only for those); the remaining non-priority candidates are not hashed and are counted as `Pile.omitted: usize` (additive, `0` when nothing was cut, `#[serde(default)]` so the JSON fixtures still load). Because an unhashed candidate is not yet known to be pending, `omitted` is a count of *changed paths not scanned*, and the notice says so (ruled text, item 1): `<shown> files shown · <omitted> more changed paths not scanned (first <cap> by path)`. `accept_all` on a truncated pile folds the rendered rows only — the omitted paths stay candidates and the next scan shows the next batch with an updated notice; nothing is ever blessed unseen. `status --json` gains `"omitted": <n>` per root (additive; `status_version` stays 1; `just golden-update`, golden shows `0`) — listed in your report as a proposed **v1.4** editorial addition to `docs/dev/engine.md`. Unit tests: a fixture with `row_cap = 3` and five pending files → three rows, `omitted == 2`, the notice text exact; accept-all → two rows, `omitted == 0`, no notice; an override at `zzz/late` with four pending files at `aaa/…` and `row_cap = 3` → the override row is present and `omitted == 1` (priority beats path order).
   - (d) Nothing else changes in the engine.
2. **`tui/app.rs` — the reducer gains the accept loop (still pure: no I/O, no engine handle).** New `Action`s: `Accept` (context: diff focus with a hunk under the cursor → that hunk; nav focus → the selected entry: `Row` = file, `Group` = group, `Root` = every row of that root), `AcceptFile` (the selected row whole, from either focus), `AcceptAll` (every listed root — the header control's key), `Confirm`, `Cancel`. New state: `RootView.pile: Pile` (the whole held snapshot — `apply_pile` compares `pile == view.pile`, so a pile differing only in `omitted` is a change, and `AcceptRequest::All` carries exactly this value); `seq: BTreeMap<PathBuf, u64>` (last seq applied per root; `apply` of a `Pile` with `seq < held` is `Changed::No` and touches nothing — the §11 hardening; the entry is **removed** when `RootsChanged.removed` names the root or `sync_roots` drops it, so a re-added root receives piles again); `accepting: Option<AcceptScope>` (in flight; a second accept while one is running is ignored with the status line `accept in progress`, exactly as `Refresh` is ignored while refreshing — ruling item 3); `confirm: Option<Confirm { scope, files: usize, grouped: usize, collapsed: usize }>` (the modal; only when the action covers **more than 10 files** — G0 Q5, hardcoded; 10 files accept without asking, 11 ask). `handle` returns `Effect::Accept(Vec<(PathBuf, AcceptRequest)>)` — one entry per root the action covers (one for hunk/file/group/root, one per listed root for `AcceptAll`) — built **from the held `RootView`s** (`Rendered::of` on the App's row; `AcceptRequest::All(view.pile.clone())`). `Accept` on a `Root` entry is `AcceptRequest::All` of that root's held pile (the fold, per ruling 5), subject to the confirm rule. `Effect` drops `Copy` (an `AcceptRequest` holds a `Pile`) and keeps `PartialEq`. Completion arrives as `App::accepted(Vec<(PathBuf, Result<Accepted, String>)>) -> Changed`: applies each root's pile through the same path as `apply` (seq included), then runs the advance rule for the accepted path, clears `accepting` once, sets one joined status line — an `Err` for one root is reported in the status (`alpha: <error>`) and does not undo the others — `accepted f1 · hunk 2 of 3` / `accepted f1` / `accepted f3 (deleted)` / `accepted upstream · 4 files` / `accepted 12 files in alpha` / `accepted 30 files in 3 repos`; on refusals, the `Refused` `Display` texts joined by ` · ` (the first only, plus ` (+N more)` beyond two); `compacted` adds nothing visible. **Advance rules (§6.7):** after accept-hunk with hunks remaining, the cursor stays at the same index clamped (the next hunk slides into it) and `scroll` follows; after the last hunk of a row, or accept-file, `accepted` applies the pile (which runs the existing `reconcile_selection` untouched — its fallback lands on the root header, which is *not* what §6.7 wants) and then applies `advance(root, path)`: the next row by path after the accepted path in the **new** pile of the same root, else the first remaining row of that root (wrap), else the next listed root's first **row** (not its `Root` entry), else nothing. `reconcile_selection` is unchanged for every non-accept path. When a root's pile becomes empty it is unlisted (existing rule). Focus stays where it was. Confirm modal: `Confirm { scope }` stores **only the scope**; its `files`/`grouped`/`collapsed` numbers are computed from the held piles at every render, so a pile applied underneath updates the numbers the user is looking at, and `Confirm` folds the piles held at that moment — the count shown and the pile folded are always the same thing (review F2; §6.7 "the confirm shows the file count"). If the scope's piles become empty underneath, the modal closes with status `nothing to accept`. `Cancel`/`Esc` → nothing; while `confirm` is `Some`, every other action is ignored except `Resize` and `Tick`. In-flight interplay (ruling 3): `Accept`/`AcceptAll` are refused with `accept in progress` **before** a modal opens, and `Confirm` re-checks — if an accept is in flight the modal stays open with that status, so a confirm is never silently dropped and never double-accepts.

## Traps (each is a verified failure elsewhere; design them out)

- **`Rendered` from the wrong place.** The CAS is only as good as the snapshot: build it from the `App`'s held row (what was drawn), never from `engine.root(..).last_pile` inside the closure — the engine may already hold a newer scan.
- **`accept_all` with a fresh pile.** `AcceptRequest::All` carries the pile the `App` held when the user confirmed. Passing the result of a new `scan` blesses content the user never saw (A5 in `01-scenarios.md` exists to catch exactly this).
- **A stale watcher pile after the accept** puts the accepted row back for one interval and the user clicks accept twice. The seq rule (1a, 2) is the fix; the parity/reducer test with an older seq proves it; the PTY loop scene sees it if it regresses (a row reappearing after `accepted …`).
- **Holding the engine mutex across `.await`** — same trap as Phase 3; `Engine::accept` is one synchronous call inside one `blocking`.
- **`Refused` treated as an error.** It is `Outcome.refused`, the call is `Ok`. Only `EngineError` becomes `Fatal`; a refusal is a status line and a re-render.
- **Double accept in flight.** A second `a` before `Accepted` returns would CAS against the same rendered oid and, if the first already committed, be refused with `baseline moved` — harmless but confusing; `accepting` gates it.
- **The candidate set is a `BTreeSet`.** Insertion order is not priority; the row cap must partition (priority set first) rather than "enumerate first".
- **Advance by index.** The row after the accepted one is found by path order in the *new* pile; indices shift when the accepted row vanishes. Selection is by path (Phase 3 rule) and stays so.
- **Confirm counts.** "More than 10 files" counts every file the action covers, including rows inside the upstream group and collapsed rows (§6.7). A group accept of 12 paths asks; `Accept` on a root with 10 rows does not.
- **`Enter`/`Esc` overloading.** They mean open/back outside the modal; the modal must swallow keys before the keymap, like the help overlay does, or `Esc` in the modal would return focus to the nav *and* cancel.
- **Proptest wall time.** 64 cases with real git per case would take minutes; the property tests stay on the in-memory `hunks` layer plus the private store on a temp dir without a repo (`RootKind::Draft` plumbing), as the existing property test does.
- **Bench in debug** measures the allocator, not the product; `just bench` builds release and the test asserts `cfg!(debug_assertions) == false` (print a skip line otherwise). Creating 50,000 files takes seconds by itself — outside the timed region, and delete them on drop (the fixture's `TempDir` does).
- **Sick FSEvents on the sponsor's Mac** (§11): the bench records which path it measured; S3's `events` line is skipped with a visible reason when the host's watcher never fires within 30 s.
- **The `+` file count** must not break the Phase 3 snapshots: only a truncated root renders it; the golden and every existing snapshot show plain counts.
- **JSON fixtures** under `crates/lastcall/tests/fixtures/` predate `Pile.omitted`: `#[serde(default)]` on the field, and the unit tests that load them stay green without regenerating.
- **`git add -A` / `git add .` are denied**; stage explicitly. `git push` never. `z_ignore/`, `scripts/harness/work/` and other worktrees are not yours. The reference clone `~/dev/git/herdr` is read-only.

## Open for ruling (orchestrator → sponsor, after the design review)

1. **Row cap value and notice text.** Rec: `row_cap = 10_000` rows per root — above the 4,000-row design scale with headroom, below the 50,000 drop; the cap's cost driver is one `hash-object --stdin-paths` batch (linear), not hunks (~0.3 ms per row). Notice: `<shown> files shown · <omitted> more changed paths not scanned (first 10,000 by path)` — "changed paths not scanned", not "pending files", because an unhashed candidate is not yet known to be pending (review F3). Alt: 5,000 with the same text — halves the worst-case batch if the S4 baseline shows the hashing batch dominating, at the price of a second batch on a large branch switch.
2. **Default accept keys.** Rec: `a` accept (context), `A` accept file, `ctrl-a` accept all, `y`/`Enter` confirm, `n`/`Esc` cancel. Alt: `a` / `A` / `*` (no control key) for users whose multiplexer eats `ctrl-a` — GNU screen's prefix, a common tmux rebind (tmux's default is `ctrl-b`), and readline's beginning-of-line; the `[keys]` table lets such a user rebind, and the docs say so.
3. **A second accept while one is in flight.** Rec: ignore with the status line `accept in progress` (mirrors `Refresh`; the accept completes in tens of milliseconds so the window is tiny). Alt: queue one — smoother under rapid `a a a`, but a queued accept CASes against a row that just changed and is refused anyway. Either way the confirm modal never opens while an accept is in flight (deliverable 2).
4. **Worker split.** Rec: three sequential (4a engine, 4b TUI, 4c e2e+bench+docs), the Phase 3 shape, because the kickoff is long and the sponsor's concern was context loss. Alt: two (engine+TUI, then e2e+bench+docs) — one fewer merge and verifier pass; fine if the engine work in 1(a–c) is judged small, but 4b is the bulk of this phase.
5. **Header Accept All scope.** Rec: every listed root (global), with the confirm naming `<N> files across <R> repos`; the per-root accept-all is `a` on the root entry. Alt: current root only, header and key identical — simpler mental model and single-root types, but the header count is global and a global control beside it reads as global. (The multi-root effect, one lock hold, and per-root error reporting are specified in deliverables 2 and 5 either way.)
