The phase exists because of one report from the sponsor's own use of `v0.2.0` (§10 2026-09-14, paraphrased there): on a feature branch an agent added thirty-two files, he accepted them as they came, and when he checked `main` out every one of them showed as a deletion he had to accept again. That is not a defect in the accept path; it is the seen-tree model's designed branch-switch over-show (§6.4: one seen record per repository, HEAD never consulted, a switch shows `switched X → Y: N files differ from seen state`). The deferral ledger already named the hardening ("No per-branch seen trees", trigger "in-place branch hopping becoming a daily pattern"); the trigger has fired. The sponsor ruled the shape the same day: **per-branch seen trees keyed by the checked-out branch, a branch's record starting as a copy of the one just left so the switch itself shows nothing new, cherry-picked content showing once more on the feature branch by design, and nothing more** ("1 rec"). Branch rows without a checkout, and "seen follows content across branches", are explicitly not in this phase.

**The framing (sponsor's instruction, 2026-09-14):** this phase adds more combinations of protective behaviour for the DX workflows lastcall sits beside, each written as a frozen scenario (D14 onward) with its harness and integration-test forms before the build. The workflows are described generically and nothing in this repository names the tooling behind them: an unattended run cuts a branch with a generated name from the current HEAD, works and commits on it, discards its uncommitted changes (`git checkout .` and `git clean -fd`), checks the start branch back out and leaves the branch in place; several such runs go back to back; later their commits are cherry-picked onto a named feature branch, so every commit gets a new id and the run branch is never an ancestor of the feature branch; a variant does the same in a linked worktree. The user wants to review and mark seen at several points in that flow.

## The model change, stated once

Today a root has one seen record: `seen_tree` ⊕ `overrides` (plus the undo stack that references their baselines). From this phase a root has **one record per branch it has been checked out on while lastcall watched**, and exactly one of them is **in force**: the record of the branch `HEAD` names. Everything that reads or writes a baseline (scan, accept, restore, flag, undo, compaction, status) works on the record in force and only on it. The rules, numbered so the design review and the sponsor can attack them one at a time:

- **R1 Which record is in force.** The branch is the name in `<git_dir>/HEAD` when it reads `ref: refs/heads/<name>` (one file read, no git process; `git_dir` is `HeadState.git_dir`, so a linked worktree reads its own). Anything else (a detached sha, an empty or unreadable file mid-write, a draft root) means **no switch**: the record in force stays in force. The sync is a `RootState`-level step (`scan_root` runs in a parallel pool over `&mut RootState`, so an `Engine` method cannot be called there): `scan_root` runs it right after `reload_ledger_if_changed`, `inspect_head` runs it before it compares heads, and `open_root_with` runs it after the ledger is loaded or first-sighted, so `scan`, `scan_all` and every head inspection see the same record and the pile depends on event ordering only inside git's own window. That window is git's, not ours: `checkout` and `switch` update the index and worktree first and write `HEAD` last (through a lockfile and a rename, so a torn read never happens; a missing file or a `HEAD.lock` can). A scan inside it compares `B`'s files against `A`'s record (over-show); an accept inside it would file into `A`'s record, which is why `Ops::commit` re-reads `HEAD` under the lock and refuses when it no longer names the branch the op was staged under (R5). The `HEAD` event, or the poll, closes the window. `inspect_head` keeps `symbolic-ref` for the label and the notice; the two agree except during a `HEAD` rewrite, and a disagreement costs a notice, never a baseline.
- **R2 First sight of a branch: a copy, then the ancestor fold.** Arriving on branch `B` from the record of branch `A`, when `B` has no parked record: `B`'s record starts as a **copy** of `A`'s (the same `seen_tree` oid, the overrides cloned, `seen_at = {HEAD, B, now}`, an empty undo stack). Then, if `refs/heads/A` still exists and `B`'s HEAD is an ancestor of `A`'s tip (`git merge-base --is-ancestor <B> <refs/heads/A>`, true when they are the same commit), the fold considers every path that differs between the two committed trees (`git diff-tree -r -z --name-only <refs/heads/A> <B>`) and, per path, lets `base` be the record's composed baseline (override blob, else the seen tree's entry, else absent), `tipA` the entry at `A`'s tip and `tipB` the entry at `B`'s tip. **The path is folded only when `base` equals `tipA` (same blob and mode, or both absent) and not when `base` is absent while `tipB` is present.** A folded path takes `tipB` in one `write_tree` fold (blob and mode from `B`'s tree; absent in `B` → removed from the record's tree), its override's blob and mode are dropped and a flag-only override stays, exactly as `ops::fold` retains flagged overrides today. Every other differing path keeps the copied baseline and over-shows. A path whose entry in `B` is a gitlink is left out of the fold (the content model cannot render it as a baseline). *(Rule tightened 2026-09-15 from the verifier's F2, ruled by the orchestrator under the sponsor's 2026-09-05 delegation: the fold as first written took `B`'s content for every differing path, which baselined a version committed on `A` while lastcall watched and never accepted, D24.)* Not an ancestor (a diverged or ahead branch, the cherry-pick case, `A` deleted, either head unborn): the copy is the record, unchanged.
  *Why the fold:* the report's own case. When `main` was never seen while lastcall watched, a pure copy of the feature branch's record carries the thirty-two accepted additions to `main`, where the working tree lacks them, and the same thirty-two deletions appear again. Going back to a branch whose every commit is already in the history you came from is the one switch that can show **nothing new** without hiding anything: `B` has no content `A` lacks. *Why not the new branch's own `HEAD^{tree}`:* that would hide the committed work of a never-seen branch at its first checkout (the run branch created while lastcall was closed, the feature branch after the cherry-picks), which is the surprise the sponsor ruled against. *Why a copy and not the fold everywhere:* on a branch that is ahead or diverged the differing committed content is exactly what the user has not seen; showing it is the over-show §2 allows. Ancestry is a one-time first-sight input here, exactly as `HEAD^{tree}` is at a root's first sight; it never enters a scan. *Why the two guards:* a path whose baseline differs from `A`'s tip is one the user has not finished reviewing on `A`, so its state on `B` must show; a path the record holds as absent has no seen content at all, so a blob on `B` must show as an addition rather than be deemed seen. The second guard over-shows one case: a path deleted in `A`'s history before lastcall first saw the root and present at `B`'s tip now shows as added on `B` instead of being baselined there; the record cannot tell that absence from an accepted deletion, and showing is the safe side. The residual the guards do not close, recorded in §11: a path accepted on `A` at its tip, cut at an intermediate commit of `A`'s history that carries a version the user never had on screen (`v1 → v1.5 → v2` accepted as one hunk, a branch at `v1.5`), folds to that intermediate blob; the hardening is an additive `before` blob on each override so the fold takes only a blob the user saw as a diff's before side.
- **R3 Parking and pruning.** Leaving `A` for `B` parks `A`'s record under `branches[A]` (`seen_tree`, `seen_at`, `overrides`, `undo`, `parked_at`); arriving on a branch with a parked record moves it out of the map and into force. At every switch the parked names are checked against `git for-each-ref --format=%(refname) refs/heads` (full names, `refs/heads/` stripped, never `%(refname:short)`, which a same-named tag can shadow) and a name with no ref is dropped (a deleted branch's record goes). Existence of a single ref is always `git rev-parse -q --verify refs/heads/<name>`, never a stat of a loose file (`pack-refs` removes the file and keeps the ref). If `for-each-ref` fails for any reason the prune is skipped for that switch: dropping a record is the fail-closed side (an over-show at that branch's next arrival), keeping one costs nothing. The record in force is never pruned. **Rename.** When the sync finds `HEAD` naming a branch other than `seen_branch` and `refs/heads/<seen_branch>` no longer exists, the record in force is re-labelled with the new name: no park, no first sight, no fold (this is `git branch -m` of the current branch, or a ref removed by hand; a switch away from a branch always leaves that branch's ref behind, since git refuses to delete a checked-out branch). A rename of a parked branch prunes the old name at the next switch and first-sights the new one as a copy when it is arrived on, an over-show by R2.
- **R4 Detached, unborn, in progress.** While `HEAD` is detached (a rebase in flight, `checkout <sha>`, a bisect) the record in force stays and accepts land in it; when a branch name returns, the same name is no switch and a different one is a switch from the record in force, with the fold's `A` being that record's branch (`refs/heads/<seen_branch>`, if it still exists). An unborn branch (`ref: refs/heads/main` before the first commit) is a branch like any other with no head: no fold. `in_progress` suppresses the notice as today; it never suppresses the switch. Bisect detaches `HEAD` without an in-progress marker, so its notices are not suppressed, as today. An operation that starts on one branch and ends on another (`git rebase main feat/x` run from `main`, `rebase --onto`) files any accept made at a conflict stop into the starting branch's record, which the finishing branch's first sight then copies: an over-show on the starting branch later, never a hide; reading `rebase-merge/head-name` to file such accepts on the finishing branch is a deliberate non-goal of this phase (§11 candidate). `git switch --orphan` empties the worktree and over-shows every file as a deletion against the copied record; `checkout --orphan` keeps the files.
- **R5 Concurrency.** A switch is a locked read-modify-write of the ledger: take `LedgerLock`, re-read the file, and if the disk's `seen_branch` already names the target (another process switched first) adopt the file and do nothing else. An `Ops` staged under branch `X` whose `commit` finds, under the lock, either the disk ledger's `seen_branch` or the `HEAD` file naming `Y ≠ X` refuses the op with the notice `branch changed under this accept (now Y); try again`, adopts the disk ledger, re-reads the tree and drops its staged overrides and pending undo entry (otherwise the next commit would re-apply the stale override into the wrong record): the rendered rows were computed against the other record. In the single-process TUI the engine's own scan performs the switch before an `Ops` is built and `accept_with` reloads the ledger on the way in, so the refusal fires only for an `Ops` built from a stale in-memory ledger: a second process (D22), or git's worktree-then-`HEAD` window (R1). When `merge_from_disk` finds the file missing or unreadable there is no disk `seen_branch` to compare and the op writes this engine's ledger, as today. Restore refuses the same way (it reads a baseline). Flag and snooze are not baseline operations and merge as today.
- **R6 Schema 1.2 (Amendment v1.12, PROPOSED).** Additive under major 1: top-level `seen_branch: "<name>" | null` (which branch the top-level record belongs to; `null` for a draft root, a detached first sight, or a file written by a 1.1 binary) and `branches: { "<name>": { seen_tree, seen_at, overrides, undo, parked_at } }`, omitted when empty; `SCHEMA_VERSION` becomes `"1.2"` and every write stamps it (Amendment v1.7's rule). **The record in force stays at the top level** so a 1.1 binary opening a 1.2 file keeps working on the branch it is on; its first write drops `branches` and `seen_branch`, which loses the parked records (over-show at the next switch, never a hide) and is a §11 residual like the flag-mirror one. A 1.1 file read by this build has no `seen_branch`: the first sync adopts `HEAD`'s branch as the record's owner **without a switch and without a fold** (nothing changes in the pile of an upgraded root; if the user switched branches while running the 1.1 binary, the record is attributed to whatever branch `HEAD` names at launch, an over-show only), and stamps it on the next write, the one rewrite of an untouched file that is not byte-identical. Absent and `null` must stay distinguishable on the wire: `seen_branch` is `Option<Option<String>>` with the ledger's existing `deserialize_double_option` and `default`, and **no** `skip_serializing_if` (a `null` written by a 1.2 binary must read back as "known, detached", never as "1.1 file, adopt"); in memory it is `Option<String>` plus a flag that says "adopt on first sync", never written.
- **R7 Nothing else moves.** Root first sight (`HEAD^{tree}`, `draft_initial`) is unchanged and sets `seen_branch` from `HEAD`. Compaction folds the record in force only. Undo pops the record in force's stack; a parked stack waits with its record. Flags are overrides and travel with their record (a flag raised on `feat/x` is not shown on `main`; it is back when `feat/x` is). Snooze stays per root. `seen_at.branch` and `seen_branch` now say the same thing for the record in force; `seen_branch` is the authoritative one, `seen_at.branch` stays the historical label it always was. The upstream annotation's range (`seen_at.head_commit..HEAD`) is now per record, which is what it always meant. Restore, editor save, the TUI's reducers: untouched; the TUI learns nothing new except the notice text (R8) and never reads a ledger.
- **R8 Notices.** A return to a branch with a parked record keeps today's text, `switched main → feat-y: N files differ from seen state`. A first sight at the **same commit** (`checkout -b`, the copy with nothing to fold) keeps today's `switched main → feat-x (same commit)` (B2, D15, D23 keep their strings). A first sight whose head moved reads `switched main → feat-x: first time here, seen state carried from main; N files pending` (B4's asserted string changes to this form, since the engine there never observed `feat-y` before the switch; D18's string is this form). `transition`'s `Checkout` arm branches on `first_sight_from` and on whether the head moved. A pure copy that was not folded and a folded copy read the same; the fold is invisible except through the count.
- **R9 `status --json`** gains two additive per-root fields (`status_version` stays 1): `seen_branch` (string or `null`) and `parked_branches` (sorted names, `[]` when none). The golden is regenerated once, in its own commit.

**D14 — Accepted on a branch, then the start branch checked out (the reported case).** Setup: `R` with 3 committed files on `main`; `git checkout -b future`; lastcall's first sight of `R` happens **here** (`seen = future's HEAD^{tree}`, `seen_branch = future`, no record for `main`). **D15 — An unattended run on a generated branch.** Setup: first sight on `main`, pile `[]`. Action: `git checkout -b run-1` (same commit; `run-1`'s record is a copy of `main`'s, the fold has nothing to do; notice `switched main → run-1 (same commit)`). An agent writes `a.rs` and `b.rs`, commits, writes `scratch.tmp` uncommitted, then `git checkout .` and `git clean -fd`, then `git checkout main`, leaving `run-1` in place. ### 2. The ledger: schema 1.2, the record type, and the switch

- Introduce a record type (name it as you like; `BranchRecord` reads well) holding `seen_tree`, `seen_at`, `overrides`, `undo`; the top-level `Ledger` keeps its fields as they are (the record in force stays flattened at the top level, R6) and gains `seen_branch: Option<String>` and `branches: BTreeMap<String, BranchRecord>` (`parked_at` on each). Wire rules: `branches` omitted when empty, `seen_branch` written as `null` never omitted once the file is 1.2 (a reader must be able to tell "detached" from "1.1 file"); the byte-identical-rewrite unit test extends to a ledger with no parked records; `SCHEMA_VERSION = "1.2"`; on the wire `seen_branch` is `Option<Option<String>>` (`deserialize_double_option`, `default`, no `skip_serializing_if`; R6) and `from_wire` lifts a missing field into `None` plus the in-memory "adopt on first sync" flag, never written.
- `parse`, `to_json`, `LoadResult`, the unreadable-file rule, the `unparsable` overrides map: unchanged; a parked record whose shape does not parse is dropped with a notice (over-show at that branch's next arrival), never the file.
- The switch itself lives in `ops.rs` as one operation (`Ops::switch_branch(from: Option<&str>, to: &str)` or the like) so it shares `LedgerLock`, `merge_from_disk`, `write_tmp` + `commit_tmp`, the tree re-read, and the fault-injection points; it pushes nothing on any undo stack. It performs R2 (copy, then fold through the existing `fold` machinery or `write_tree` directly: the fold input is the record's composed baseline for the differing paths replaced by `B`'s tree entries, read with `cat-file --batch`/`ls-tree` from the user's repository through the store's alternates), R3 (park, load, prune with one `for-each-ref`), R5 (re-read under the lock, adopt if already there).
- `RootState::sync_branch(&mut self, …)` (private) reads `<git_dir>/HEAD` (R1) and calls the switch when the name differs from `ledger.seen_branch` (or adopts, for the 1.1 case; or re-labels, for R3's rename); it is a no-op for a draft root (`repo == None`) and when `HEAD` is detached, unborn-and-unnamed, missing or locked. Call points: `scan_root` right after `reload_ledger_if_changed` (so both `scan` and `scan_all` reach it), `inspect_head` before the head comparison, and the tail of `open_root_with` after the `LoadResult` match (root first sight already sets `seen_branch` from `HEAD`, so the sync is a no-op there), which is where an offline switch (D21) lands before the first scan. `Ops::set_override` and `Ops::commit` are crate-private, so the switch lives inside `ops.rs`.
- `Ops::commit` and the restore path get the R5 branch check; the refusal is an `Outcome` refusal with the given text, so the TUI shows it on the status line exactly as a CAS refusal.
- Unit tests, each named: the wire round trip of a 1.2 file with two parked records; byte-identical rewrite with none; a 1.1 file adopts without a fold; the fold math on a fixed pair of trees (ancestor: differing paths take `B`'s entries and lose their overrides; not an ancestor: the copy is identical to the source, overrides included); prune drops only names without refs; the unreadable-HEAD and detached cases perform no switch; an accept staged under one branch is refused after a switch by another `Ops`; compaction after a switch touches the record in force only; undo after a switch pops the right stack and an empty one refuses as today; `blob_override_count` counts the record in force only.
