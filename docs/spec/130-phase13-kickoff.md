## The sponsor's rulings (verbatim in §10; summarised here)

1. **The scroll position stays a line of the diff, not a row of the screen.** `DiffCursor::scroll` keeps its meaning (an index into header + lines + separator per hunk). The renderer wraps. Nothing that stores or compares a scroll position changes meaning.
2. **One wrapped line never fills the pane.** A line that would wrap to more rows than the cap is cut at the cap and its last row ends in `…`. The cap is a few rows short of the pane's body height, so the line after it is always at least partly on screen.
3. **Wrap is on by default, and it has a toggle.** `alt-z` is bound (the key VS Code users know). A second, plain-character binding exists because Option/Alt does not reach every terminal (`docs/config.md` already explains this for `alt-up`). The sponsor ruled the plain key is **not** `shift-w`: "it's not semantically close to what 'w' does". A config default exists: `[ui] wrap = true`. Both keys are rebindable under `[keys]`.
4. **Break at a word boundary; hard-break a word longer than the row; the `+` / `-` gutter and the colour repeat on every continuation row.**
5. **The index and marker hardening from §11 goes into this phase** ("lock rec") as a second, separate deliverable with its own tests. Which of the two hardenings §11 names is the orchestrator's call under the delegation; the design review moved it from a new lock file to the ledger lock (deliverable B).

**Orchestrator taste-calls, labelled as such (the design review accepted the first, F24):** the plain key is **`c`** (clip or wrap; free today, as is `x`), and the action is named **`wrap`**. The default bindings are **`["c", "alt-z"]` in that order**: `hints` shows the first bound key (`render.rs:588`), and the help overlay shows every key whatever the order (design review F11). The hint tells the truth about the state, as `hide_empty` does: `c clip` while wrap is on, `c wrap` while it is off. A continuation row's marker is drawn dim so a wrapped `+` line does not read as three added lines (F19).

## Deliverable A: visual word wrap

### The model

- **One pure layout function, used by everyone.** A new module (suggested `tui/wrap.rs`) holds (a) `wrap_words(text, width) -> Vec<(usize, usize)>`: char ranges, break after the last whitespace that fits, hard-break a run longer than the row, always at least one range, never an empty range except for an empty line. **A row is measured the way ratatui draws it** (F12): the width of a candidate row is `UnicodeWidthStr::width` of the row's text (already a dependency), not a per-char sum, because an emoji written with a variation selector is two cells to `Buffer::set_line` and one to a per-char sum, and the difference clips the row's last character. **Corrected by the code review (verify-a F1):** this rule was false about ratatui, which draws grapheme by grapheme with its own `CellWidth`; the width of the row as one string is a different number for some scripts, and the built rows clipped their tails. The code measures with ratatui's own segmentation (`Span::styled_graphemes`) and cell width, and breaks only between the clusters it draws; still no new dependency. Never break immediately before a character whose own width is zero (a combining mark, a variation selector, a joiner). `cell_width`'s tab arm is dead here (`line_text` expands tabs first). No new dependency: `unicode-segmentation` is not a direct dependency and is not added. **Every character is kept** (F18): this is a diff, so nothing is dropped or collapsed; whitespace that fits stays on its row, whitespace that does not fit leads the next row, a run of whitespace wider than the row breaks like an over-long word. `tour.rs`'s `wrap()` collapses whitespace and must not be reused; and (b) the pane layout: given the hunks, the scroll line, the body's columns and rows, and the wrap flag, the list of screen rows, each naming its line index and which part of that line it is. The renderer draws from that list, the hit map is that list, and the `App`'s keep-visible arithmetic asks the same function. **No second implementation of "which line is on which row" may exist.**
- **Width.** The text wraps at `body columns - 1` (the gutter column). A continuation row repeats the gutter character (` `, `+`, `-`) and the colour. Leading indentation is not repeated on continuation rows (taste-call: it costs the columns a narrow pane does not have). The hunk header row does not wrap: it clips as today, and its controls, marker, target and band are untouched.
- **The cap.** `cap = body_rows.saturating_sub(3).max(1)`; the promise that the next line is partly on screen holds when the body has more than three rows. A line that wraps to more than `cap` rows draws `cap` rows, and its last drawn row ends in a marker drawn **dim, never in the line's green or red**, so it cannot be read as content (F15): ` … +N` where N is the count of characters not shown, falling back to `…` alone when that does not fit. The marker occupies the row's last columns; content that would overlap it is dropped from that row by whole characters (a wide character is never halved). `y` on a capped line copies the whole line, which is the documented way to read the rest. With wrap off the cap does not apply.
- **The scroll.** `diff.scroll` is still a line index and the top row of the body is always the first row of that line. `j` / `k` move one line, which may be several rows; accepted by ruling 1. **Nothing may skip a line** (F13, F16): a wheel step of `n` lines and page down are clamped so the new top line is at most one past the last line that was fully on screen (exactly one forward when only the top line fit). Page up is a backward fill: the old top line is fully on screen afterwards. Both move at least one line unless at the end. Page up is **not** page down's inverse with rows of different heights, and no test may claim it is. The scroll's maximum stays `lines - 1` and the end jump is unchanged (`scroll_by`, `clamp_cursor`, `jump_diff_end` do not assume row = line; do not improve them).
- **Geometry the `App` needs.** The renderer writes the body's size back (`hits.diff_body` already carries the rect; `run.rs` copies columns and rows into the `App` beside `nav_top`). Before the first frame, after a `Resize` (where `run.rs` clears the hits: clear the copied size at the same point, since up to 256 events fold before the next draw), and when the body was not drawn (`area.height == 0`), the `App` falls back to a new `diff_cols()` beside `editor_cols()` (the pane's inner width, without the editor's gutter) and `page_rows()` (F17). Two call sites draw hunks (`:1626` the expansion, with a shorter body, and `:1652`); the size written back is the one that drew. `move_sel_cursor` keeps the selection's end fully on screen using the layout function. `move_hunk` is unchanged.
- **Hit testing.** `HitMap` gains the row table (`diff_rows: Vec<usize>`, one line index per drawn body row). The table carries **every** drawn row: headers, text rows, continuation rows and separators, so header clicks (`Target::DiffHunk`) and separator presses answer what they answer today. `diff_line_at` looks the row up there; a row inside the body but past the table's end answers the **last line** (today's effective behaviour after `SelectTo`'s clamp, F14); a point outside the body answers `None`. Every row of a wrapped line selects that line.
- **Bands.** The selection band and the current-hunk band cover every row of a line they cover.
- **The toggle.** `App` gains `wrap: bool`, initial value `config.ui.wrap`. Action `wrap`, default bindings `["c", "alt-z"]`. Toggling keeps `diff.scroll` and redraws. The hint (`c clip` / `c wrap`, or the user's first key through `hint_label`) sits beside `select` and `copy` in reading order and is **first in `HINT_DROP_ORDER`** (pinned by a test: a hint outside that list is never dropped and would overflow the line), so at 100 columns with a full line it does not show and those frames do not change (F25); it shows only where the diff pane has hunks. The help overlay lists it on the second page with the other view toggles, described as `wrap long lines` (15 columns, inside `describe`'s 30; `c / Alt-z` fits the 14-column key field).
- **Config.** `[ui]` table, `UiConfig { wrap: bool }`, default `true`, `deny_unknown_fields`. `wrap = "yes"` and `[ui] wrapp = true` are load errors with the usual message shape (pattern: `config/mod.rs:679`, `:698`). The value reaches the `App` the way `hide_empty` does (`commands/tui.rs:82`). `lastcall config` prints the effective config and gains `[ui]`.

## Deliverable B: the index is seeded only under the ledger lock

### The defect (from §11, PLAUSIBLE, not reproduced)

`seed` is three steps with nothing held across them, and the fold seeds after it drops the ledger lock. Process A, still on tree X, and process B, folding to tree Y, can interleave as: B removes the marker, B `read-tree Y`, A removes the marker, A `read-tree X`, A writes marker X, B writes marker Y. The index now holds X under a marker that says Y, every later `ensure` for Y calls it fresh, and a file accepted into Y and then put back to its X content is not listed. That is a hide, and it persists until something else reseeds. The root of it is two things: a seed is not atomic against another seed, and **a process whose ledger is out of date may seed the tree it still believes in**.

### Why not a new lock file (the first draft of this section, withdrawn by the design review)

The first draft added `index.seed.lock` and held it across every scan's read of the index. The review showed what that costs: two panes on one repository is the normal setup and both scan on the same file event (F6), so every scan would contend; a busy lock after a committed accept would report the accept as failed (F2); a failed scan is never retried and `lastcall status` prints an empty pending list with exit 0 for a root whose scan failed (F3); `flock` has no re-entrancy, so the acquisition point and an order against the ledger lock would have to be policed (F5); and the hold had to reach `others` as well (F1). The §11 entry named a second hardening, and it has none of those costs.

### The fix (as corrected by the second design review, G1 to G12)

1. **Every seed happens while the ledger lock is held, and `index.rs` exposes exactly two ways to seed** (G8). The raw `seed` becomes private to `index.rs`. (a) `seed_committed(&LedgerLock, tree)` for the fold, which wrote the ledger under that same lock and so needs no check. (b) `ensure` and a `reseed` for the scan's two sites (`scan.rs:350`, `:361`), which acquire the lock themselves, do the checks of item 3, seed, and **drop the guard before returning**, so `scan.rs` never holds a guard and none can outlive `ensure` into the retry. `PrivateIndex` keeps a `RepoPaths` clone (it is built from one at `engine.rs:925`; `scan::scan` has no paths today) and a `lock_budget: (u32, Duration)` defaulting to `(LOCK_RETRIES, LOCK_BACKOFF)` with a setter for in-crate tests: that is where zero-budget tests get their budget (the engine gives every `Ops` `DEFAULT_LOCK`, and `fold` ignores `self.lock`, `ops.rs:2292`). One lock, so no lock order; the new nesting is ledger lock then git's own `index.lock`, and no holder of `index.lock` (a git child) ever asks for the ledger lock. No new file, no new dependency, no `libc`, no `unsafe`.
2. **The fold seeds before it drops the lock, best-effort.** The fold's tail, in order (G9): best-effort `seed_committed`, then `drop(_lock)`, then `staged.clear()` and `ls_tree` as today (`ls_tree` stays outside the lock; its `?` at `ops.rs:2490` already returns `Err` after the commit today and is not this phase's). On a seed error the fold makes a second best-effort attempt to remove the marker and returns `Ok` whatever that attempt does. **`Ops::fold` and everything that calls it never returns `Err` because of the index** (G4: `Engine::accept_with` still runs `self.scan(root)?` afterwards, `engine.rs:1520`, which is today's behaviour and §11's entry, not this phase's).
3. **The scan's stale path, under the lock, in this order:** (i) re-read the marker; if it now names the tree to seed and the index looks like an index, return without seeding (G5: a fold in another pane may have just seeded it, and a redundant `read-tree` zeroes the stat data and forces a whole-tree content refresh under the lock). (ii) **Read and parse `ledger.json` and compare its `seen_tree` with the tree about to be seeded** (G1): `std::fs::read` plus `ledger::parse` (`ledger.rs:704`), **never `ledger::load`**, which moves an unparsable file aside. Seed when they are equal, or when the tree to seed is `None` (an empty index over-shows, and it covers a process that cannot use the tree the disk names because its store lacks it). Otherwise touch nothing and return a typed `LedgerMoved`. **As built and kept by the code review (verify-b F3, F4):** a read or parse failure is its own typed `LedgerUnreadable`, which a reload cannot answer and which is therefore not retried, and an **absent** `ledger.json` lets the seed go ahead, because every writer of a seen tree saves the ledger under this lock before it seeds, so an absent file has no newer tree to be stale against (the verifier attacked this arm and could not break it; refusing instead would make one deleted file a permanently failed scan). Not the stamp: the stamp moves on every flag, snooze and plain accept, none of which move the tree, and `reload_ledger_if_changed` can hold a new stamp over old content. (iii) Fix that at its source too: `reload_ledger_if_changed` (`engine.rs:255`) stores the stamp only after a successful read and parse.
4. **`seed` aborts if it cannot remove the marker** (G6): a removal error other than `NotFound` returns before `read-tree`. Otherwise "removal failed, `read-tree` succeeded, marker write failed" leaves the new index under the old marker, the defect's own end state.
5. **A scan that found the marker fresh takes no lock, and validates its read afterwards** (G2). `ensure` returns the marker file's identity as it read it (mtime, length and inode of `index.tree`; every seed replaces it by rename). After `others` (`scan.rs:365`), and after the retry path's `diff_files` and `others`, the scan stats the marker again; a different identity or a missing marker means the index was reseeded under this scan, and the scan returns a typed `IndexMoved`. Identity, not content: a later fold can return to an earlier tree. Without this, a reseed between `diff_files` and `others` can omit a path that is pending under both the reader's tree and the new one (the review's schedule S2: an added file folded by another pane and then edited, inside one scan), and a one-shot `lastcall status` has no next scan to correct it.
6. **`LedgerMoved` and `IndexMoved` loop the whole of `scan_root`** (reload, `sync_branch`, `trim`, scan), bound 2 (G12; a lock-held reload is not simpler, because `sync_branch` and `trim` take the ledger lock themselves). On exhaustion: `LedgerMoved` is returned as the error; **`IndexMoved` returns the last pile with a notice**, which is what every scan does today, so no new failure reaches `accept_with` or `status` from it.
7. A busy ledger lock on the stale path is the existing `LockBusy`. **Corrected by the code review (verify-b F2):** it reaches the pane wrapped as a scan error, so it shows as a failed scan and not as the accept path's `ledger busy` line; mapping it to that line would tell the user to retry an accept that landed. It is a member of §11's scan-failure entry. `read-tree` of a large tree is tens to a few hundred milliseconds, inside the 2 s budget; only folds and stale scans pay it.
8. **Facts the verifier should not have to re-derive:** the callers of `seed` are exactly `scan.rs:350` (through `ensure`), `scan.rs:361` and `ops.rs:2492`; `switch_branch` and `fold_onto_first_sight` (`ops.rs:2187`) move the tree and rely on the next `ensure`; `undo` never moves the seen tree (`ops.rs:1772`). `StoreGit`'s use of the shared index is read-only (second review, confirmed). `refresh` (`index.rs:166`) rewrites `index` from every scan with no ledger lock, so the rule is "seeded only under the lock", not "written only under the lock"; that unlocked writer is safe because `git update-index` takes `index.lock` before it reads the index (PLAUSIBLE from git's source, `builtin/update-index.c`; the verifier confirms it for the installed git). "No ledger-lock holder touches the index while holding it" was a fact about the code before this phase; the fold is now the deliberate exception. A failed or stale pile in a pane lasts until the next worktree event or the 30 s backstop, which marks every root due (`watcher.rs:733`, `:777`), whichever is first.
9. **What this does not fix, said plainly in the CHANGELOG** (G7): the fix holds between processes that all run it. An older lastcall on the same repository still seeds unlocked, so panes should be restarted after the upgrade. Judgment call, not taken: changing the marker's text so the first new scan reseeds once; an older binary would then reseed on every scan, and two versions side by side would each force the other's whole-tree content refresh, the slowness Phase 12 removed.
