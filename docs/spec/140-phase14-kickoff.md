## Deliverable A: `review_ignored`

### The model

- **Config.** `review_ignored: Vec<String>`, a top-level key of `Config` beside `draft_dirs` (there is no `[roots]` table; the sub-tables are `[ui]`, `[herdr]`, `[update]`, `[keys]`), default empty, under the struct's existing `deny_unknown_fields`. Each entry is one gitignore pattern (`z_ignore_*`, `**/*.scratch.md`, `/notes-*.md`); git's grammar, so `docs/config.md` says "a pattern as you would write it in `.gitignore`". `validate` refuses an entry that is empty or whitespace, one that begins with `!` (the negation is ours to add), and one containing a newline or NUL, with messages in the shape of the `draft_dirs` ones (`config/mod.rs:459-476`). A leading `/` anchors the pattern to the repository root and is allowed (`!/z_ignore_*` lists the root file only, verified); git drops an unescaped trailing space from a pattern, so the docs say to escape one with `\ `. Grammar note the docs row carries (design review F12): to review a whole ignored folder, name it with a trailing slash (`z_ignore/`); `z_ignore/**` cannot re-include anything inside an ignored folder, because git never descends into one; a pattern that matches an ignored nested repository lists that repository as a nested root (which `skip_globs` can then remove). `docs/config.md` names the grammar and the base of each pattern key side by side (F25): `review_ignored` is gitignore grammar against the repository root; `skip_globs` and `draft_dirs` are globset (`literal_separator`) against the parent directory; `ignore_globs` is globset against the root.
- **The mechanism, and why it is the whole engine change.** A git root's listing is `ls-files --others -z --exclude-standard [--exclude-from=<info/exclude>]` (`others_args`, `index.rs:414-436`). For each entry, in config order, append `--exclude=!<entry>` after the existing arguments (the position is a choice, not a requirement: a command-line pattern wins over `--exclude-from` and `core.excludesfile` in either order, verified). Git applies command-line patterns above every ignore file, so a matching file is listed as an ordinary untracked candidate. **Verified by the orchestrator on git 2.37.1** in a throwaway repository with `z_ignore_*` in `core.excludesFile`: `--exclude='!z_ignore_*'` lists `z_ignore_top.md` and `sub/deep/z_ignore_note.md` (every depth) and does not list `z_ignore/inside.md` or `target/z_ignore_built.md` (a file inside an ignored directory cannot be re-included; git's rule). `check-ignore` still reports such a file as ignored, so nothing may be built on `check-ignore`. Draft roots get no `--exclude` at all: their listing never used `--exclude-standard` (`index.rs:422`).
- **Threading.** `OpenCtx` (`engine.rs:887-892`: `env, layout, clock, draft_initial`) gains the pattern list; `PrivateIndex::new` (`index.rs:121`: `git, paths, kind, exclude_from`) gains it too; `open_root_with` (`engine.rs:894`, the call at `:928`) passes it for `RootKind::Git` only. With `review_ignored = []` the argv is **byte-identical** to today's, asserted by a unit test.
- **Downstream, nothing new.** Once listed, the path is an untracked candidate (`scan.rs:471-478`): pending on first sight (ruling 3), hashed, hunk-reviewed, accepted into the seen tree, removed by an accepted deletion. No badge (ruling 4), no new row kind, `status --json` unchanged in shape (`RowStatus`, `status.rs:111-127`, has no untracked marker today and gains none).
- **Removing an entry later: an honest over-show, stated in the docs and the CHANGELOG.** A file accepted while the entry was in force keeps its seen-tree entry. With the entry gone, `others` stops listing it, but `diff-files` still compares the private index (seeded from the seen tree) with the disk, so a later change to that file, or its deletion, is still a row until accepted. Nothing is hidden, and every such row is clearable by one accept. *(Orchestrator's Rec under the delegation; Alt, not taken: a trim through `git check-ignore --stdin` over the record's untracked paths at every scan, a git call per scan for a case that ends in one keypress. The design review is asked to judge this.)*

## Deliverable B: `[seen] N files`

### The model

- **Where it lives.** Annotation is a layer after the scan, not inside it: `upstream.rs::annotate` is called from `scan_root_once` at `engine.rs:1258`, failures become notices, never dropped rows. B adds `seen.rs` beside it, called at the same point, after upstream. `scan.rs` stays ignorant of HEAD and of parked records.
- **What is compared.** For a git root with at least one parked record (`ledger.branches`), each row with `current: Some(Present { oid, mode })` (never an absent path, never `Unhashable`) is compared with the composed baseline of that path in each parked record: the record's override (`blob: Some(Some(oid))` with its `mode`) if it has one, else its `seen_tree`'s entry. An exact match on both `oid` and `mode` marks the row `seen_on = [branch, …]`. The record in force is never compared (a match there would not be pending). An override of `Some(None)` (seen as absent) or a flag-only override never matches.
- **Cost.** `Store::ls_tree` lists a whole tree (`store.rs:668-677`); parked trees are listed nowhere today. B lists each parked record's tree once and caches it in `RootState` keyed by `(branch, tree oid)`; a parked tree changes only when a switch parks a record, so every scan after the first hits the cache. No git call per path. A root with no parked record costs nothing new. Three rules the cache and the matcher follow (F17): the cache drops entries for branches `prune_parked` removed, so it cannot grow with every deleted branch; overrides are read live from the parked record (`ledger.branches[b].overrides`), never cached; the comparison goes through the scan's mode normalisation (`norm`, `scan.rs:640-700`) and treats an override carrying a blob with `mode: None` as `Mode::Regular`, as `BaselineResolver::baseline` does (`ledger.rs:958-960`); and no `ls_tree` runs when the pile is empty. `switch_branch` copies the parked record's `seen_tree` oid and overrides into the new record before folding (`ops.rs:1940-1950`), so the `(branch, tree oid)` key stays right across a switch.
- **The fold (ruling 5, ruling 10 Rec).** A marked row that carries **no flag of its own** (a note rides on a flag; an accept-only override is not a reason to stay, because a compaction folds it into the seen tree and the fold must not change with a compaction: verification F1, ruled at close-out) and is not half of a rename pair leaves the nav list and joins one entry `[seen] N files`, rendered where the `[upstream] N files` entry is (`nav_entries`, `app.rs:1594-1610`: after the rows), selectable, with `Target::NavGroup`. This is the one place the phase departs from the upstream shape, and it is the sponsor's ruling: upstream rows stay listed with a badge, seen rows fold. A marked row that **is** flagged, or is half of a rename, stays its own row with the short badge `[seen]`, because a flag and its note are the user's and a rename is accepted as a pair. The pile itself is unchanged: `Pile.rows` keeps every row, and **`RootView::rows()` keeps returning every row** (its callers `counts_of`, `rows_in`, `render_header` and the accept path go by the whole pile, and the accept-all modal must count exactly what `AcceptRequest::All(pile)` accepts; design review F3). A new `RootView::nav_rows()` (the rows minus the folded paths) feeds `nav_entries` and the nav renderer only; `counts_of` counts a folded path under `grouped seen` the way it counts `grouped upstream`, so the modal's total stays the pile's and the `CONFIRM_ABOVE` threshold cannot be folded under. Typing (F16): `Group.kind` becomes a `GroupKind { Upstream, Mixed, Seen }` and the row gains `seen_on: Vec<String>`; the `Annotation` enum stays the row's, so a row is never annotated `Seen`; `Pile::groups()` yields the seen group, so `RootStatus::of` (`status.rs:206-215`) lists it with no TUI code. When the selected row folds after a scan, `reconcile_selection` moves the selection to the group row, not to the neighbour. `status --json` and `lastcall status` therefore keep listing every row.
- **The expand exit (ruling 10).** The `expand` action (`e`, `Action::Expand`) on the selected group row opens it: `nav_entries` then lists the group's members directly after the group row, in path order, as indented sub-rows (the ordinary row rendering with a two-column indent and the `[seen]` badge; `HitMap` entries like any row), each an ordinary `Selection::Row`, so the diff pane, `m`, `u`, `a`, `A`, `i` and `y` all work on a member exactly as on a row. `e` on the open group row, or on one of its members, closes it and the selection moves to the group row. The open state is one flag per root in `App` (beside the view), kept across scans for the session and cleared when the group disappears; it is not persisted. A member that gains an override (a flag, a note, a snooze) leaves the group on the next render by the fold rule and becomes an ordinary `[seen]` row above the group, the group's count drops by one, and the group stays open for the rest. `request_expand` today requires a `Selection::Row` on an expandable collapsed row (`app.rs:1657-1678`): the group case is a new arm before it, not a change to it, and `Effect::Expand` is not involved (opening the group is pure state, no engine call). The group row's hint reads `e expand` when closed and `e collapse` when open, beside `A accept`; the help overlay's `expand` description covers both if the width test allows, else stays. `docs/review-loop.md` shows the closed and the open group.
- **The right pane.** Selecting the group shows the header `N files, content accepted on <branch>` (two or three branches listed, more as `on 4 branches`), then one path per line as the upstream group view does (`render.rs:1339-1348`), each followed by its branch when the pane is wide enough; when it is not, the header alone names the branches and no per-path branch is shown (F23).
- **Accepting.** As for upstream: `a` on the group refuses with `A accepts the group` (`app.rs:1945-1948`); `A` takes `AcceptScope::Group` and the loop sends `AcceptRequest::Group { rows, rendered_on }` to `Ops::accept_group` (`ops.rs:895`), one undo entry, the status text `accepted [seen] N files`. `z` undoes it. `ctrl-a` (accept all) counts them in its modal the way it counts `grouped upstream` (`test_e2e_tui_snapshots.rs:1085-1100`).
- **Nothing is hidden, ever.** Property, tested: for any pile, the nav's rows plus the seen group's paths equal the pile's rows; the group's count equals its list's length. A file whose content differs from every parked baseline, however slightly, is a row. A pending deletion is a row.
- **Upstream and seen together.** A row annotated `Upstream` or `Mixed` keeps that annotation and is never marked seen (upstream is older and means "someone else's commit"); it stays in the upstream group and the seen group does not count it. Stated in the docs; tested.
- **Pruned and stale records.** `prune_parked` runs only inside `switch_branch` (`ops.rs:1926`, `:1970`), so a branch deleted while the user stays put keeps its parked record until the next switch, and its content keeps matching until then. Accepted as is (the record is the user's accepted content; the branch name in the header is what it was); stated in `engine.md`.
- **`status`.** The human form prints `[seen] N files` under the repository like the upstream line; `status --json` rows gain `seen_on: [branches]` (empty when none) and `groups` gains an entry of kind `seen`; additive; the golden regenerated in its own commit.
- **D16 amended (v1.15).** The scenario's pile is still `[a.rs, b.rs, c.rs]` in the engine (the test `scenario_d16_cherry_picks_show_once_more_by_design`, `test_integration_scenarios_d.rs:1356`, keeps its pile assertion and gains `seen_on == ["run-1"]` / `["run-2"]` per row); the TUI shows `[seen] 3 files`; accepting the group leaves `[]`; `main`'s record untouched; restart identical. The sentence "hiding it would require seen-follows-content, which this phase does not do" stands: the seen tree is not moved, the rows are pending, they are folded.

## Deliverable D: `R` reloads the config

### The model

- **Action `reload`, default `["shift-r"]`.** In `DEFAULT_KEYMAP` (`input.rs:466-536`; `shift-r` is unbound today), placed directly after the `refresh` row (`:510`; the table is the help overlay's display order and the comment at `:513-517` explains the 80×24 fold, F28), `Action::describe` ("reload the config file", 22 columns), the `[keys]` grammar (rebindable, an upper-case letter is spelled `shift-r`), the help overlay row, the hint line beside `refresh` where it fits (appended last in `HINT_DROP_ORDER`, `render.rs:558-575`, so it is the first hint dropped).

A plain `request_rescan` cannot carry a reload: the rescan block (`:740-777`) emits only when the diff is non-empty, so an edit that changes only `ignore_globs`, `[keys]` or `collapsed_globs` would never reach the watcher and the notice would never land (F4); (e) that signal's discovery pass lands after (c) the way `spawn_set_search_depth` orders it (`run.rs:868-872`); the `RootsChanged` it produces reinstalls watches and drops or adds roots, and every root is then scanned as after any rescan. `RootsChanged` also closes a confirm modal whose root left, with the status text `<name>: no longer listed` (F19).
- **What a reload cannot apply, said in the notice and in the docs.** `[herdr]` (the `HerdrPlan` is moved into the connect task after the first frame, `run.rs:1690-1691`) and `[update]` (the closure is consumed once when the launch hold ends, `:2068-2074`): when either differs from the running config, the notice adds `herdr and update settings apply at the next launch`. The state directory and the config path are the environment's and are never reloaded; the first-launch marker is not re-read. `draft_initial` is read when a root is opened, so a change applies to roots opened after the reload and an open root is never re-first-sighted; `search_depth` and `draft_dir_parents` land through the discovery pass (F14). A reload applies the file's `search_depth`, so the tour's failed-write card (`write.rs`, "add by hand") says that `R` applies the line once added (F29).
- **The notice.** `config reloaded` followed by what changed: `2 roots added`, `1 root removed`, `keys`, `ui`, `watcher` (ignore globs), `collapse` (collapsed globs or size), and the next-launch sentence when it applies; `config reloaded, nothing changed` otherwise. The root counts come from the `RootsChanged` the reload's discovery produced, so the notice is posted when that event lands, not when the key is pressed; the status line reads `reloading…` in between, the way `refreshing…` does.
- **The parent-key consequence, stated plainly.** A repository that a reload finds under a different `parent_dirs` entry than before is a new root in the state layout (§6.1, ruling 8 parked): it is first-sighted, and its old record stays where it was. `Engine::rescan` diffs discovery by path today and never refreshes `RootState.parent` (`engine.rs:763-782`, `:195-330`), so without a rule the reload would keep the old state and the next launch would file the repository under the new parent and first-sight it there (F5). The rule: `Engine::rescan` treats a surviving path whose `parent` changed as removed-then-added, closing its `RootState` and opening it under the new parent id, so reload and restart agree; the notice counts it under `roots added`; `docs/config.md` says so beside the key. *(Judgment call under the delegation; Alt, not taken: apply a parent change only at the next launch, which would make `R` and a relaunch disagree on the same file.)*

Inside `discover` the match is against that parent-relative path. Inside a draft root's scan the candidates are root-relative bytes and `ScanCtx` carries no parent (`engine.rs:1100-1130`), so the engine builds, per draft root at open and at reload, a skip GlobSet from the entries with that root's own parent-relative prefix stripped (an entry that neither starts with the prefix nor begins with `**` cannot match below the root and is dropped), and the scan matches root-relative candidates against it (F13). The discover-side filter is what removes a clone reported before the key was added (`RootState.nested_repos` persists, `engine.rs:215`); the scan-side filter only stops new reports.
- **Two effects, one key.** (1) *Repositories:* inside `discover`, before anything is opened: every root of `RootKind::Git` whose relative path matches is never inserted into `Discovery.roots`, whatever found it (the level walk, a scan's nested report, `worktrees_inside`, a linked worktree's main). The skip match runs on every candidate directory **before** `has_git_entry`/`record_git_root` in the walk and before the nested promotion's `toplevel`, so a skipped repository costs no spawn (today the walk calls `record_git_root` for every child with a `.git` entry before any filter, `roots.rs:215-262`, F8). A directory is matched both as `rel` and as `rel/`, so a pattern `evals/**` prunes the folder `evals` itself (globset's `/**/` matches zero components, but `evals/**` alone does not match `evals`). A root that is itself a `parent_dirs` entry or the launch directory is never skipped (a notice says the pattern was ignored for it): so `skip_globs = ["r"]` with `parent_dirs = [W]` skips the level-1 repository `r`, while with `parent_dirs = [W/r]`, or launched inside `r`, `r` stays with the notice (F9; A9 says the same). The level walk does not enter a plain folder whose relative path matches, the way it does not enter a `WALK_SKIP` name, so a skipped tree of clones is never read at launch. Because the skip is part of every discovery pass, it holds at launch (a matching repository is never opened: no `open_root_with`, no git spawned for it, no index seeded) and later (a clone appearing under a skipped path is never promoted; an entry added to the file and reloaded with `R` drops the roots on that pass). (2) *Watched folders:* a draft root whose own path matches is not a root; inside a draft root that stays, a candidate whose parent-relative path matches is dropped where `excluded_dirs` are dropped (`scan.rs:471-478`, `:515-538`), and a `NestedRepo` under it that matches is not reported for promotion. The watcher's `ignore_globs` stays a separate, watcher-only key.
- **The boundary, stated in the docs.** `skip_globs` never reaches a repository's own files: a tracked or untracked file inside a listed repository is reported whatever the key says, because no key may hide a real change (the sentence `ignore_globs` carries today, `docs/config.md:63`). The sponsor asked "either match"; this is that, with the repository's own contents outside it. *(If the sponsor wants it to reach inside repositories too, that is a separate ruling with the cost named: the first key that can hide a tracked edit.)*
- **Consequences, stated.** A skipped repository's files are reviewed by nobody (git treats a nested repository as opaque, already true today). A skipped repository's state on disk, if it was ever listed, stays. Adding or removing an entry takes effect at the next discovery, so it composes with `R`. `lastcall status` honours it.

1. **One selection model, two sources of lines.** `Sel { anchor, cursor }` stays.
