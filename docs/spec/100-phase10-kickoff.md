## Deliverables

### 1. The first-launch overlay (sponsor item 1, ruling R1: Rec)

**What.** On the first `lastcall tui` ever run against a state directory, once the launch hold and the scope verdict are past, an overlay opens over the live screen: a keys card, then up to two cards that appear only when their condition holds, each offering to change one default and remember it. It is shown once; `lastcall tui --tour` shows it again.

**The marker.** `<state_dir>/first-launch.json`, `{ "shown_at": <unix seconds>, "version": "<binary version>" }`, written tmp + rename (the `write_stamp` idiom) when the overlay is dismissed by any path: finished, skipped, or the process quitting with it open (`Effect::Quit` from `q`'s non-printable spellings or `ctrl-c` writes the marker before `restore_terminal`). Absent, unreadable or unparsable means "show"; headless commands never read or write it. `--tour` ignores the marker for that run and rewrites it on dismissal. **The too-small path writes nothing** (F12): at widths under 60 or heights under 14 the overlay does not open and the marker stays absent, so the tour opens on the first launch that is large enough; the check is one `stat` per launch until then.

**When it opens.** At the first render where `loading.is_none() && !herdr.scope_pending` (the same instant `is_listed` first admits a root). Not before: the conditional cards need the link state and the empty-repo count. If the run ends before that instant, nothing is written and the next run shows it.

**Where it lives.** A `tui/tour.rs` module (state, cards, `tour_action`, rendering) and, for the config write, a **`config::write` module in `lastcall-engine`** next to `Config::parse` (it owns `Env`, `config_path` and the parse); `toml_edit` is an engine dependency. Both add hits to the `OpenOptions|File::create|fs::write` gate greps in `tui.md`: deliverable 5 updates those two rows with the new sanctioned files.

**The cards, in order.** Wording is final unless the sponsor changes it; keep the shape (a title, two to four lines, a footer of keys). House style: no em-dashes, no process vocabulary, no exclamation marks except the one in the herdr card. **The key column of the keys card is rendered from `keys_for(action)` like the help overlay** (F15): a user with a `[keys]` table on first launch sees their own bindings; the strings below show the defaults.

### 2. Undo the last accept (sponsor item 2, ruling R2: Rec)

**What.** `z` (action `undo`) reverses the most recent accept in the selected root: a hunk, a file, a group, a deletion, an accept-all, or an editor save that blessed the file. A stack of the last **20** per root, persisted in the ledger so it survives a restart and is shared by every lastcall over the same state directory. Undo never touches the working tree; it only makes things pending again.

**The record.** Ledger schema stays `1.1`; `Ledger` gains an additive field, serialized last:

```json
"undo": [
  { "op": "accept_hunk | accept_file | accept_group | accept_deletion | accept_all | save",
    "at": "<iso8601>",
    "paths": { "<root-relative-path>": { "baseline": "<blob oid> | null", "mode": "100644 | 100755 | 120000 | null" } } }
]
```

`baseline` is what §6.2's resolution answered for that path **immediately before the op** (`Present` records the oid and mode; `Absent` and `Empty` both record `null`, which is safe because the restoring write goes through `set_override`, below); `mode` likewise. `op` names what was staged: an `accept_hunk` on a deletion row records `accept_deletion` (F20). Cap: when the stack has 20 entries the oldest is dropped. An `accept_all` entry lists every path the fold took from the snapshot (the row cap already bounds that). A refused accept, `compact`, restore (`u`, `shift-u`) and the flag ops push nothing.

**Where the push happens** (F2). `merge_from_disk` replaces the ledger wholesale, so the entry cannot be pushed onto `self.ledger` before `commit`, and after the replay the merged overrides already hold the new blob, so the pre-accept baseline can no longer be read there. Mechanism: `Ops` gains `pending_undo: Option<(UndoOp, Vec<String>)>` beside `staged`, set by the staging functions (`stage_file`, `stage_deletion`, `accept_hunk`'s write, `save_file`) with the op kind and the staged keys; `merge_from_disk` resolves each key's baseline from the **on-disk** ledger and tree **before** replaying `staged`, pushes the entry onto `merged.undo` (capping at 20), and clears the field; the `Missing`/`Unreadable` early return resolves against `self.ledger` and pushes there instead. `fold` computes the accept-all entry between its merge and its `retain`, from the overrides and tree as they stand before the fold. The entry and the accept are therefore one ledger write. A unit test opens a second `Engine` over the same state directory after the first's accept and sees the entry (precedent `ops_commit_merges_with_a_ledger_written_by_another_engine`).

**The operation** (F1). `Ops::undo(fault) -> Result<Outcome, OpsError>`: lock, merge from disk, pop the top entry, and for each path call **`set_override(key, baseline, mode)`** with `baseline: Option<Oid>` (`None` for a null record), never write the override directly. `set_override`'s `equals_tree` rule then does the right thing in every case: a recorded oid equal to the tree entry drops the override (the §6.2 clean-up rule, and the path stops counting toward compaction); a null on a path the tree has keeps `Some(None)` = `Absent`, which is correct after any fold; a null on a tree-less path drops the override so the path resolves to `Empty` again, and a later `shift-u` writes a zero-byte file instead of unlinking the user's first-sight draft (the F17 case). `flags` are preserved and `updated_at` stamped by `set_override` itself. One ledger write; `staged` cleared. The stack being empty is a refusal (`Refused::NothingToUndo`), not an error. No CAS on the live content: a file that changed since the accept is exactly what the user wants to see again. A second lastcall that accepted the same path after this entry has its own entry on top; LIFO order makes that the one `z` pops. **Fail-open** (F13): a recorded baseline whose object is gone (a git root whose user ran `gc` after a rebase) resolves like every missing object, to the tree with a notice; a unit test deletes the baseline object from a draft store (no alternates) and pins that behaviour.

**Compaction is not a boundary.** A unit test forces the threshold to 1, accepts three files (folding each), undoes three times, and asserts the pile equals the pile before the first accept. A second test does the same across two `Ops` over one ledger directory (the second opened after the first's writes). A third asserts a flag on a path survives its accept and its undo. A fourth is the F17 case: a draft root at `draft_initial = pending`, a new file, `accept_file`, `undo`, `restore_file`: the file is zero bytes, not gone.

**The channel to the UI** (F8). `Pile` gains `undo: usize` (additive, `#[serde(default)]`), stamped by the engine from the ledger at every scan; `Accepted { pile }` carries it after an accept and after an undo. The hint, the status suffix and a second process's undo depth all come from there.

**UI.** `z` in either pane acts on the selected root (the root of the selected row, or the selected root row). Status line: `undid accept of <path>` for a single path, `undid accept of <n> files in <root>` otherwise, `nothing to undo in <root>` on refusal. After an undo the selection moves to the first path of the entry (path order) once the pile arrives, so the file reappears under the cursor; with the diff pane focused it stays focused. `ctrl-a` across roots pushes one entry per root; `z` undoes the selected root's top entry and the status line adds ` (<k> other repos have their own undo)` when other roots' piles report a depth that grew from the same accept-all. Hint line (F14): `undo` joins `HINT_DROP_ORDER` between `hide_empty` and `jump`, offered only when the selected root's `undo` depth is non-zero; `snooze` is not on the hint line (the help overlay carries it). Help overlay row: `z  undo the last accept in this repository`.

**`status`**: `--json` gains additive per-root `undo` (integer, the stack depth); `status_version` stays 1; the golden is regenerated and the status doc updated. The human report appends ` · <n> undo` to a root's line when non-zero (F18).

**Tests.** Unit: the record's exact JSON shape; push on every accept family and on a blessing save, with the op name checked (`accept_hunk` on a deletion row records `accept_deletion`); no push on refusal, restore, flag, compact; the cap at 20; the four tests above; the fail-open test; the second-engine test; a 1.1 file without the field loads with an empty stack. PTY: `tui_undo_file` (`shift-a` on a three-hunk file, then `z`: the file is back with three hunks, the status line says so); `tui_undo_accept_all` (30 files over two roots, `ctrl-a`, confirm, `z`: the selected root's files are back, the other root's are not, the status line names the other root). ### 3. Snooze a repository (sponsor item 3, ruling R3: Rec)

**What.** `s` (action `snooze`) on a **repository row** in the nav hides that repository for a number of days, default 1; `shift-s` (action `show_snoozed`) shows the snoozed ones for the session; `s` on a shown snoozed repository wakes it. A snoozed repository is still watched and still scanned: like the workspace scope, snooze is a view, not a filter, and the headless commands are unaffected except for reporting it.

**The record.** `Ledger` gains an additive top-level field `snoozed_until: "<iso8601>" | null`, written under the lock by `Ops::snooze(until)` and `Ops::unsnooze()` (each: lock, `merge_from_disk`, set the field on the merged ledger, write, clear `staged`; the field is set after the merge, never before, F2). Schema stays `1.1`. An expired value is treated as `null` by every reader and cleared on the ledger's next write. Draft roots snooze like git roots (`RootKind::Draft` has a ledger).

**Time** (F4). The engine decides expiry with its injected `Clock`, never the TUI: `Pile` gains `snoozed_until: Option<String>` (additive, `#[serde(default)]`), stamped at scan time from the ledger with an expired value already `None`; the `Ops::snooze` result carries the same. For a snooze that expires while the TUI is open, the loop hands the reducer a wall-clock instant from the engine's `Clock` on each `Tick` (`App.wall: Option<SystemTime>`), and the `Tick` reducer, not `render`, compares and re-lists (`reconcile_selection` when a root comes back). Unit tests inject a `FixedClock`; the snapshot tier sets `wall` by hand; no `SystemTime::now()` under `tui/`.

**UI.**

- `s` with anything but a repository row selected: status line `select a repository row to snooze it`, nothing else.
- `s` on a repository row opens a small modal in the note modal's shape: `snooze <name> for [1] day(s)`, the number editable with digits and backspace, range 1 to 365, `enter` applies, `esc` cancels. On apply: the ledger write, the repository leaves the nav, the selection moves to the entry that takes its place (§6.7 as amended by v1.9), the status line says `snoozed <name> until <YYYY-MM-DD>`.
- The bottom line's count (F6): beside the existing scope notice, `· <k> snoozed (S shows)` whenever `k > 0`; when both a scope count and a snooze count exist they are separated by ` · `. `render_status` has no tiers, so give the combined notice a rule: when the full form would leave the status text or hints fewer than 30 columns, drop the parentheticals (`scope: alpha · 2 hidden · 1 snoozed`), and below that drop the scope label (`2 hidden · 1 snoozed`). The 80-column snapshot with both counts must show a readable `snoozed <name> until <date>`.
- `shift-s` flips a session flag `show_snoozed`; while on, snoozed repositories are listed with a dimmed suffix on the branch line, `snoozed until <YYYY-MM-DD>`, and `s` on one of them wakes it (status line `woke <name>`), no modal.
- A snoozed repository whose herdr flag has attention is listed regardless, exactly the `hide_empty` exception, with the same suffix.
- `is_listed` gains the clause (`pile.snoozed_until` is `None`, or `show_snoozed`, or attention); the header count follows it.

**`status`**: `--json` gains additive per-root `snoozed_until` (`null` when not snoozed or expired); `status_version` stays 1. The human report appends ` · snoozed until <date>` to a root's line (F18).

**Tests.** Unit: the field round-trips; expiry at the boundary through the injected clock, in the engine's stamping and in the `Tick` reducer; the modal's number editing and range; `is_listed` with snooze on, expired, shown, and with attention; a draft root.
