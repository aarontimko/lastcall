## Deliverable D: a PTY scene never sends a bare `Esc` a key can merge into

### What exists (facts at `dd069a7`)

- `select_until` (`crates/lastcall/tests/test_e2e_tui_pty.rs:1301-1331`) sends `\x1b` unconditionally, then waits up to 400 ms for the header text; when the header is already on screen the wait returns at once, before the program has read the byte. The next `send` in the caller then lands in the same read and crossterm parses `Esc` plus the key as `Alt-<key>`. The macOS `integration` job of the `v0.6.0` release ci run failed exactly so (`pty_seen_group_cherry_pick_expand_flag_accept_undo`, the third `A` lost; §11 2026-09-27). 22 call sites.
- The help-overlay scene guards the same coalescing by waiting for the overlay to close (`test_e2e_tui_pty.rs:5166-5178`); the reload scene guards it with a 50 ms sleep (`5557-5558`); the other bare `Esc` sends (2391, 2559, 2953, 4249, 4433) each wait for the modal they close.
- `back` is bound to `esc`, `h` and `left` (`input.rs:475`); `h` is not an escape prefix. In the nav `back` clears a live right-pane text selection (`app.rs:4657-4661`, `Changed::Yes`) and, once B lands, a range; otherwise it changes nothing. `h` equals `Esc` only outside the note, picker and snooze modals (they own every key), the confirm (which passes only confirm and cancel) and the inline editor (`app.rs:4545-4598`); today no `select_until` site is inside any of them (F8).
- The hint line shows the focus (`↑↓ select  ⏎ open` with the nav focused, `↑↓ scroll  ← back` with the diff focused; `docs/dev/tui.md`, the hint line row), but not while a status message owns the bottom row (`render.rs:501-540`), which is the case in the failing scene.

### The model

1. `select_until` sends `h` instead of `\x1b`: the same action, no ambiguous prefix, nothing to wait for. The comment says why. A scene that rebinds `back` away from `h`, or calls it inside a modal or the editor, would need its own helper; the worker's audit lists each of the 22 call sites with its keymap and the screen state at the call (nav, diff, help, a modal, the editor) and reports that none does either (F8).
2. The reload scene's `Esc` (`5557`) closes the help overlay after a `?`, which any key closes; the hazard there was `Alt-q` closing the overlay and eating the `q`. It becomes `h` followed by the wait the help-overlay scene already uses (`5166-5178`, "any key closes" gone from the screen), and the 50 ms sleep goes (F9).
3. A rule in `docs/dev/tui.md`'s PTY-harness section: a bare `Esc` is sent only when the scene then waits for the visible effect it causes; where `Esc` only means `back`, send `h`.

### Tests first (D)

- No new test can fail deterministically on the old helper (the race is timing); the evidence is the audit: the report lists every `send(b"\x1b")` left and the wait that follows each, and the 22 `select_until` sites' keymaps and screen states. `just test-e2e` green; the PTY count stated.

No multi-row state exists (`nav_anchor` is scroll bookkeeping, `4048-4092`; `Sel` is the right pane's text selection, `1191-1201`).
- A click: `render_nav` (`render.rs:932-1129`) pushes `(rect, Target::NavRow(root, path))` per visible row; `Ui::event` (`run.rs:353-399`) turns a left press into `Action::Press(x, y)`, resolves it through `hits.at` and calls `App::hit` (`app.rs:5037-5143`; `NavRow` at 5117-5119). A press in a pass already marked changed is held and replayed against the next frame (`run.rs:577-590`, `tui.md:119-123`).

- The PTY encoder has press, release and drag, no shifted press (`pty_tui.rs:781-810`); SGR 1006 spells a shifted left press as button 4 (`\x1b[<4;col;rowM`), which crossterm decodes into `KeyModifiers::SHIFT`.

### The model

1. **State.** `App.range: Option<RangeAnchor>`, `RangeAnchor { root: PathBuf, path: Vec<u8> }` (named apart from `nav_anchor`, the scroll bookkeeping; F15): the anchor is a row path, never an index. The range is the contiguous run of file rows (`view.nav_rows()` rows, `folded` false) of `nav_entries()` between the anchor and the current selection, both file rows of the same root; a helper `range_rows()` walks the entries and stops at any `Root` or `Group` entry and at any open seen group's member (members are `Selection::Row` entries too, pushed after the `Group` entry at `app.rs:1771-1776`, so stopping at `Group` alone would admit a run of members; F5). `select()` clears the range except on the extend path; `reconcile_selection` drops the range when either end no longer resolves (a member vanishing in the middle shrinks it, since it is defined, not stored). `back` clears it; so does the wheel over the nav, which moves the selection like a plain move (F15).
2. **Actions.** `extend_down` (`shift-j`, `shift-down`) and `extend_up` (`shift-k`, `shift-up`): with the nav focused and a file row selected, set the anchor if none and move the selection one entry, keeping the range; refuse (no change, `Changed::No`) when the neighbour is not a file row of the same root, an open seen group's member included, or when the selected row is itself such a member (F5). With the diff focused they do what `nav_down`/`nav_up` do not: nothing (`Changed::No`). `Action::ShiftPress(x, y)` from a left press whose modifiers contain `SHIFT` (`mouse_action`): resolved through the hit map; on a `NavRow` of the selected row's root with a file row selected it is `extend_to(row)` (anchor set if none, selection moved, range kept); any other target behaves as a plain press. Held and replayed exactly as `Press` is.
3. **Accept.** `AcceptScope::Rows { root, paths }`. `accept_file_scope()` yields it while a range is live; `accept_scope()` (the hunk key) refuses with "`A` accepts the N selected files" (the key spelled from the keymap as the group refusal does). `accept_requests` builds one `AcceptRequest::Group { rows, rendered_on: pile.seen_branch }` over the range's rows in nav order; `counts_of` tallies the same rows, so the confirm threshold and the hint agree by construction. No engine change. Completion: `accepted N files in <root>`; the advance rule selects the entry taking the range's place; the range is cleared.
4. **Everything else per row.** `a`, `m`, `shift-m`, `u`, `shift-u`, `e`, `enter`, `i` act on the selection (the cursor end) only.
5. **Render.** `NavLine.in_range`; a member that is not the cursor row is drawn `REVERSED | DIM`, the cursor row plain `REVERSED`, so the `_styles` snapshot tells them apart. The right pane shows the cursor row's diff, unchanged; the header's `[A accept file]` label follows `accept_file_scope()`: a new label `A accept N files` beside the group's `A accept group` (`render.rs:666`; F11).
6. **Hint line.** While a range is live the accept phrase reads `A accept N files` (N from `counts_of`), in the accept slot, offered only when N > 0. No new drop-order entry.
7. **Docs.** `docs/config.md` action table (two rows), `docs/review-loop.md` (one paragraph: a run of rows, the keys, shift-click inside herdr), `docs/dev/tui.md` (the state, the reducer arms, the hit-map rule for `ShiftPress`, the key table, the mouse paragraph rewritten so it says which half works where), `CHANGELOG.md` `## Unreleased` `### Added`, README's one-line key list if it names `shift-a`.

### The model

1. **`prep` moves to the branch.** `just release-prep <version>` runs on any branch but `main`, clean tree. Guards, in order: a valid version; not on `main`; clean; the version later than `Cargo.toml`'s and later than the newest `v*` tag on `origin` (after `git fetch --tags`); `origin/main` an ancestor of `HEAD` after the fetch, since branch protection requires an up-to-date branch (`publishing.md:58-67`) and an update-merge made later would put a merge commit after the bump (F3); the tag absent locally and on `origin`; `## Unreleased` present and non-empty (or an rc's dated `## <base>` as today); the install pages naming the shown version exactly twice each (final versions). It edits the same five files the same way and commits `chore(release): <version>` on the current branch. No `release/v<version>` branch. The undo line names `git reset --hard HEAD~1` only when the commit was made. A release candidate is prepped and tagged from its phase PR the same way; the final after it is a one-commit branch and pull request made the same way (`just release-prep 0.7.0` on any branch name), and `prep` has no path on `main` (F7). Two branches prepped to the same version conflict on `Cargo.toml` and `CHANGELOG.md` at merge, a safe failure.
2. **`tag` gains one guard; `merge`'s "next" line uses it.** `tag` refuses unless `HEAD` is a merge commit (two parents) whose first-parent diff (`git diff HEAD^1 HEAD -- Cargo.toml`) changes the `[workspace.package]` version line: the merge that brought the bump and nothing merged after it. Under one pull request per release every `just merge` is a candidate, and a dependency or docs merge landing between the phase merge and the tag would otherwise ship under the phase's number with none of its testing (F2). `merge`'s "next: just release-tag" line applies the same predicate to the merge commit it just made (`gh pr view --json mergeCommit`), never to the PR's head commit alone, so an update-merge on the branch does not hide the bump (F3). Everything else in both verbs is unchanged.
3. **The record is written before the tag, and ticked after.** The §8 gate line "`v<version>` released by the tag on this PR's merge commit" and the amendments' "ratified by the merge of this PR" are written in the PR unticked, since neither event has happened when the PR is opened; the next PR to `main` (the next phase's kickoff, normally) ticks both with the tag object and the release run id, as a required line of its entry baseline, and updates `operations.md`'s evidence table (line 140) in the same commit. No post-release pull request; nothing is ticked before its event (F6).
4. **The self-test.** `python3 scripts/release.py self-test` covers the pure helpers (version parsing and ordering, the CHANGELOG dating, the install-page substitution, the tag-and-version guards over a fake `ls-remote` output) with no git and no network; `just lint` runs it, so CI covers it on both runners, and `release.yml` runs `just lint` too, so it runs again on the tag (F14).
5. **Docs.** `operations.md` release recipe (24-54) rewritten to: `just release-prep <version>` on the phase branch, push, one pull request, `just merge`, `just release-tag`; the invariants (86-100) kept; the "three pull requests" history in one sentence. `justfile` comment block and recipes; `AGENTS.md` golden path line and the operations stub; `release.py` docstring; the kickoff convention sentence in this file (below, under Docs).
6. **§10 entry** "2026-09-27 (the release flow)" with the sponsor's words and the superseded 2026-09-17 ruling named.
